# 基础阶段任务介绍

## 一、任务背景

小公司或工作室通常同时存在邮件整理、会议纪要、制度问答、代码审查和代码编写等需求。本任务要求搭建一个可供不超过 10 人使用的本地大模型服务，并开发配套测试与展示系统，观察不同工作负载和并发条件下的表现。

完成部署后，请根据测试数据识别性能问题，选择一项或多项指标进行优化。项目最终提交源码、配置、原始结果与书面报告，并能够演示服务异常后的恢复过程。

## 二、周期与开发环境

任务周期为一周。具体截止日期和时间以任务发布通知为准，请在截止时间前完成 GitHub 提交。

- 自行准备具有相应显存容量的 NVIDIA 独立显卡，在 WSL 中部署运行。
- 推理引擎使用 llama.cpp／llama-server，模型使用兼容的 GGUF 格式。
- 使用 AI 辅助编码工具，并在报告中说明使用范围与核验方式。
- 根据显存、上下文容量、办公与编程表现选择模型，记录来源、版本、量化格式和文件校验值。
- 模型全部计算层及推理 KV 缓存放在 GPU；配置 GPU 推理并关闭主机 RAM prompt cache，使基础阶段的缓存工作集驻留显存。
- 模型权重与 KV 的主机内存／磁盘卸载留在进阶方向。文件读取、HTTP 服务、前端和测试脚本按常规方式使用主机内存。
- 保存启动配置、加载日志和 GPU 监控记录，核对计算层、KV 位置与显存余量。

## 三、基础功能

### 1. 本地推理服务

完成模型加载、请求调用与流式输出。系统能够接收纯提示词，也能够读取指定文件，将文件内容与关联提示词组织为模型输入。文件中的说明和代码作为待分析素材，任务指令以测试提示词为准。

模型输入应满足所选模型的上下文限制，为生成预留空间。记录聊天模板处理后的实际输入 token 数及输出上限。

### 2. 性能测试与文件存储

开发可重复运行的测试程序，支持选择提示词、关联文件、运行配置、重复次数和并发数。结果按运行编号保存，至少包括：

- 硬件信息、软件版本、模型信息、服务配置及测试负载。
- 请求 ID、提示词编号、文件校验值、实际输入 token 数、输出 token 数和输出内容。
- 提交、首个有效生成内容、完成等时间点及相关耗时。
- 成功、失败、超时、取消等状态，错误类型与错误信息。
- 基线和优化后结果、配置差异及汇总统计。

请保留逐请求原始记录，以便复核汇总结果。数据格式可选择 JSON、JSONL、CSV 等，并在开发说明中解释字段。

### 3. 前端展示

前端能够展示服务状态、测试配置、请求执行状态、模型输出、性能统计及错误记录，并支持查看基线与优化后结果。至少覆盖单并发和多并发结果。

**ps：你可以将流式对话和文件读取功能集成到前端展示中；**

### 4. 报错记录与服务恢复

实现服务状态检测、异常记录、进程重启及恢复就绪确认。通过一次运行中的服务退出验证恢复流程，记录异常时间、恢复时间、受影响请求及其最终状态。

对等待请求、已发送请求和失败请求分别定义处理方式；采用重试时设置次数上限，并处理重复请求和重复计数。服务恢复后执行请求，验证推理功能已恢复。

## 四、规定输入与输出检查

使用 [测试提示词](提示词与输入文档/测试提示词.md) 中的 10 个任务，保存相应输出。输入包括 4 个纯提示词任务、4 个关联办公文档任务及 2 个关联源文件任务。

办公任务检查事实准确性、事项完整性、格式和条款引用；编程任务检查问题定位、修复正确性、可执行性和边界覆盖。对失败输出给出具体样例，说明其对应用场景的影响。

输入提示词、关联文件、系统消息与聊天模板合计控制在 50,000 tokens 以内，同时满足模型的上下文容量。若需使用精简版本，保存版本、截取范围、校验值及实际 token 数，并在基线与优化测试中使用同一版本。

## 五、场景与并发测试

确定一个不超过 10 人的小公司或工作室场景，说明办公与编程任务的比例、请求长度、输出长度及到达方式。使用规定任务组织固定负载。

- 测试单并发和至少一种多并发，最大并发为 10。
- 说明客户端并发数、服务 slot 数及请求排队方式。
- 每种核心配置至少完成 3 轮相同负载测试，记录请求顺序、到达时间和重复方式。
- 将冷启动、预热和正式测试区分记录；说明缓存复用、服务重启及缓存重置方式。
- 保持模型、输入、输出限制、硬件和统计方法一致，比较配置变化的效果。

## 六、性能优化

选择一项或多项指标优化，可以从批处理、并行 slot、上下文容量、Flash Attention、KV 精度、模型量化或其他有依据的**配置与实现**调整入手。（提示：有时候仅仅改动配置参数就能实现性能大幅提升）

建议观察的指标包括：

| 指标 | 记录要点 |
| --- | --- |
| TTFT | 客户端提交请求至首次收到有效生成内容，包含客户端可观察的排队与传输 |
| TPOT | 明确计算公式及是否排除首 token；说明客户端测量与服务端生成耗时的区别 |
| 吞吐量 | 明确统计窗口、生成 token 总数或成功请求总数，以及失败请求处理方式 |
| 请求完成耗时 | 包含排队、提示词处理、生成和传输；给出中位数和 P95 |
| 显存占用 | 记录模型加载后、测试过程峰值及配置变化 |
| KV 容量（token） | 在模型与 KV 均驻留 GPU 的条件下，记录配置总容量、各 slot 可用容量和实测可用容量；说明共享池或分槽方式、KV 精度、并发数及验证边界。容量覆盖输入及已生成 token，区分配置值与实测值 |
| 成功率与恢复耗时 | 给出分母、状态分类、异常发生与恢复完成的判定 |

流式响应的一个数据块可能包含多个 token，请按实际 token 数统计。记录吞吐提升伴随的延迟、显存和输出效果变化。

选择 KV 容量作为优化目标时，在相同模型权重和显存条件下比较优化前后的可用 token 容量，并同时观察速度和输出效果。逐步增加上下文长度或并发上下文总量，记录已验证容量及出现容量不足、上下文截断或推理失败的位置。结合服务配置与加载日志确认容量口径，输入长度继续遵循本任务的 50,000 tokens 上限。

优化过程包括问题定位、改动、配置差异、基线对比与结果分析。允许使用和改造开源项目，请注明版本、来源及自己的开发内容。
