# 参考测试

本目录提供一个虚构的 7 人工作室场景，便于开始缓存和调度实验。同学们可调整、扩展或使用自己的材料，保留负载定义和版本即可。

## 材料

- [测试提示词](测试提示词.md)：8 类办公、资料问答与编程任务。
- [参考请求序列](参考请求序列.jsonl)：16 条固定请求，包含交互、后台和突发到达。
- [知识库 v1](输入文档/工作室项目知识库-v1.md)与[v2](输入文档/工作室项目知识库-v2.md)：相同业务的两个版本，用于检查更新后的复用与事实正确性。
- [编程文件](输入文档/batch_export.py)：批量导出示例，用于代码分析与改造请求。

文档和源文件作为资料输入，指令采用关联的测试提示词。模型推理由学生实现的系统调用，输入材料与 `development/` 中自行组织的项目代码分别管理。

## 请求序列字段

| 字段 | 含义 |
| --- | --- |
| request_id | 本轮中的唯一请求编号；重复运行时增加运行编号 |
| arrival_offset_ms | 相对正式回放开始的计划到达时间 |
| user_id / session_id | 用户和资料会话的组织标识 |
| prompt_id | 对应测试提示词编号，关联文件由提示词定义 |
| task_type / interaction_mode | 业务属性，可用于查表或模型判断 |
| deadline_after_arrival_ms | 示例业务期限，从计划到达时刻起算 |
| suggested_output_budget_tokens | 输出预算起点，按模型与任务调整并固定 |
| business_context | 用于理解业务重要性的文字背景 |

序列含 7 个用户和 16 条请求，用户数与推理并发数分别配置。回放程序按计划到达投递，将等待压力留在队列，记录实际投递偏差。期限和输出预算是场景初值，可按硬件调整并保存版本。比较时保持同一版本。

序列提供业务属性，优先级由学生的规则或决策模型产生。用于检验判断方法的场景约定与核对样例可自行编写，保存到配置和测试中。

## 缓存实验

1. 使用 v1 执行 T04、T05，观察共同文档前缀的复用。
2. 交替请求文档和代码，观察多个条目竞争缓存容量。
3. 完成一次请求后重启服务，再执行相关任务，比较恢复与重算。
4. 切换到 v2 执行 T06，检查设备借用、回访期限和备份保留期是否采用新值。
5. 扩展不同文档长度、缓存预算和冷热比例，记录命中与传输成本。

短材料适合验证流程。性能实验可编写更多有明确事实的资料，形成不同长度版本，并记录 tokenizer 计数与校验值。将固定资料放在输入前部、变化问题放在后部，记录实际 token 前缀与模板。

## 调度实验

参考序列起始包含后台任务，随后出现交互和短期限请求。固定到达顺序比较先进先出与自己的策略。通过压缩到达间隔、延长输出、重复批次等方式形成排队压力，说明采用的负载版本。

观察各类请求等待、完成和期限达成情况。分别固定优先级来源或调度策略，分析判断与调度的贡献。持续加入高优先级请求时，检查低优先级任务的执行机会。

## 输出检查

资料版本事实见对应文件；T06 应使用 v2 的最新规则。编程任务通过实际执行模型生成的代码与样例进行检查。统计时保留全部请求状态，关联输出文件和检查记录。
