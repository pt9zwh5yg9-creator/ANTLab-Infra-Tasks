# 进阶阶段提交标准

## 一、GitHub 提交

任务周期为一周，具体截止日期和时间以发布通知为准。Fork 本仓库，在自己的仓库中开发，并在截止时间前推送完成的作品。

提交信息包含：GitHub 仓库链接、最终分支、commit SHA，以及开发说明、报告和主要数据的位置。最终分支可设为默认分支，也可在仓库首页明确标注。使用私有仓库时，提前提供考核人员访问权限。

按开发过程组织提交，使用能说明功能、修复或策略改动的 commit 信息。使用已有项目时保留来源与基线版本，使本阶段改动可查看。

## 二、作品内容

| 提交内容 | 说明 |
| --- | --- |
| `development/README.md` | 选题、系统结构、环境、运行方式及复现入口 |
| 自己实现或修改的代码 | 自编模块、开源项目适配、引擎修改或可应用的补丁 |
| 配置与依赖信息 | 模型与服务配置、策略配置、固定负载、基线及优化配置；依赖的来源、版本及获取方式 |
| 测试 | 策略与状态验证、输出检查、异常和恢复测试 |
| 原始记录与结果 | 逐请求记录、策略事件、输出、资源记录与统计 |
| 书面报告 | 完成的 Markdown 或 PDF 报告及配图 |

`development/` 的内部目录由同学们自行组织，各项内容的位置在 `development/README.md` 中列出。源码可以只提交自己实现或修改的部分，依赖的完整源码通过项目链接、版本或 commit 获取；自己的改动应能定位、查看和复现。

引擎改动通过 fork 版本与 commit、子模块或可应用的补丁记录，并在运行说明中解释复现方式。模型、构建产物、环境和大型 KV 数据放在本地，仓库保留获取信息、校验值及可复查的小型样例。

## 三、验收依据

### 问题与实现

- 场景、问题、优化目标和判断依据明确。
- 有可运行的开发内容，关键策略可从源码、日志及相关展示追踪。
- 开源代码、基础阶段继承内容和自己的改动说明清楚。

### 测试与结论

- 基线合理，负载和变化项有记录，核心比较至少运行 3 轮。
- 原始结果能够支持报告结论，成功、失败、取消和重试有统一计数口径。
- 展示优化收益、资源代价和模型输出效果。
- 覆盖能够暴露方案边界的情境，并呈现异常处理与恢复结果。

### 方向相关内容

- KV 选题：呈现缓存匹配、复用、容量与失效等选定策略的实际执行；区分各层 token 容量及活跃工作集。
- 调度选题：说明优先级来源和调度逻辑；呈现判断耗时、实际执行次序、各类请求延迟及公平性。
- 自主选题：定义适合本项目的功能和优化指标，用测试证明目标完成情况。

### 展示、报告与 Git

- 展示关键运行状态与基线对比，可采用日志、图表或前端。
- 报告包含问题、实现、数据分析及可复现索引。
- 能解释关键代码与策略，并演示配置或策略调整。
- Git 提交历史、版本管理和运行说明便于查看与复现。
- AI 辅助编码及开源项目的使用范围、版本和核验方法明确。

## 四、演示准备

从仓库说明启动系统，演示选题对应的真实流程、基线与优化差异，以及一次相关边界或异常情境。围绕实际代码、策略执行和数据进行交流。
