# 方向一：KV 缓存管理与复用优化

## 参考场景

一个 7 人工作室反复查询同一项目文档、分析代码或继续已有会话。服务可能重启，文档也可能更新。可以管理 KV 的保存、匹配、恢复和淘汰，减少重复提示词计算，并探索显存、内存和磁盘之间的资源分配。

## 可以从哪里开始

可以基于 llama-server 的 slot 保存／恢复接口开发代理服务，也可以改造开源项目或引擎。缓存代理负责组织请求、查找缓存、协调 slot 和记录事件；推理由 llama.cpp 执行。

[llama-server 官方文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)提供推理、slot 状态和缓存快照接口；[hearth-llm](https://github.com/caporalCoder/hearth-llm)可作为持久化缓存代理的代码参考。按所用版本确认接口和行为，记录适配改动。

## 设计问题

| 问题 | 可选思路 |
| --- | --- |
| 保存什么 | 完整会话、固定文档前缀、可复用的上下文段或引擎 KV 块 |
| 如何匹配 | token 前缀匹配、会话索引、内容校验值；关联模型、模板和运行配置 |
| 如何处理更新 | 文档版本变化、模型变更和缓存不兼容时更新索引或重新计算 |
| 如何分配容量 | 最近访问、访问频率、条目大小、重算成本或自定义策略 |
| 何时加载 | 请求触发、提前预加载，或结合队列和预计访问进行预取 |
| 如何协调并发 | slot 预留、缓存亲和性、恢复操作与请求执行的互斥 |
| 如何分层 | GPU 活跃工作集、内存缓存、磁盘保存；设计迁移和淘汰策略 |

同学们自行确定策略、数据结构和实施层次。文件快照代理可作为起点，GPU 内部的分块迁移与异步传输可通过引擎改造进一步探索。

## 建议验证情境

1. 同一文档、不同问题：观察复用量与 TTFT。
2. 不同会话交替使用：观察缓存选择及 slot 分配。
3. 服务重启后继续请求：比较恢复与重新计算的耗时。
4. 文档从 v1 改为 v2：核对新版本事实和缓存更新。
5. 缓存预算缩小、访问冷热混合：检查淘汰及收益。
6. 缓存缺失、恢复失败或请求取消：检查状态、回退与后续请求。

使用不同长度和复用比例测试，分析缓存读写成本与重算成本的关系。多级 KV 方案同时观察传输开销和输出效果。

## 记录与展示

记录缓存条目、版本、token 数、所在层、大小、命中、保存／恢复、迁移和淘汰事件。前端展示容量、事件和策略效果。

可用指标包括命中率、复用 token 比例、TTFT、吞吐、各层容量（token）、GPU 活跃工作集、读写／传输耗时及资源占用。区分配置容量、实测容量、保存历史量和实际参与当前推理的上下文。
