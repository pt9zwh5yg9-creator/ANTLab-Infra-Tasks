# 方向二：请求优先级判断与调度优化

## 参考场景

工作室多人同时使用推理服务，既有客户演示中的即时问答、故障排查等交互任务，也有文档整理、批量代码审查等后台任务。开发调度服务，结合请求特点和运行状态安排执行机会。

参考结构：请求进入 → 优先级判断 → 等待队列 → 调度与 slot 分配 → llama-server → 输出与状态记录。

## 1. 自行设计优先级来源

| 方式 | 示例 |
| --- | --- |
| 规则或查表 | 根据角色、任务类型、交互方式、业务期限和明确约定查表或计算 |
| 决策模型 | 使用 JEV 等模型判断紧急程度、业务重要性或任务类别，将结构化结果映射到优先级 |
| 混合方式 | 规则处理明确情形，模型辅助语义判断，再结合等待时间和系统状态调整 |

[JEV 官方文档](https://docs.typesafe.ai/introduction)介绍结构化判断；[Score](https://docs.typesafe.ai/primitives/score)可以按自定义等级描述返回评分。等级含义、组合方式、映射阈值及异常处理由同学设计，也可以使用其他适合的模型和方法。

预先定义场景中的优先级约定和典型样例，再检查判断结果。可以考虑用户声明与实际任务信息冲突、资料不足、表述变化、模型判断超时等情况。记录判断依据与处理决定。

## 2. 自行设计调度策略

优先级判断提供请求属性，调度策略决定何时执行、由哪个 slot 执行以及如何使用资源。同学们自行设计策略，可以研究：

- 同优先级请求按到达时间、长度、期限或其他因素排序。
- 低优先级请求等待越久，如何获得更多执行机会。
- 长短请求混合时如何兼顾交互响应与总体吞吐。
- 如何利用输入长度、输出预算、KV 容量或缓存命中情况。
- 如何控制并发、处理取消、超时、重试和服务恢复。
- 如何进一步实现运行中抢占、状态保存和续跑。

请求先保留在自己的等待队列，获得执行资格后发送给 llama-server。可以使用 slot 查询和指定 slot 的能力，但外部查询与分配之间应协调状态，保证实际执行符合策略。

等待队列调度可从服务层实现。运行中抢占涉及生成状态、KV 和资源释放，其实现与验证范围在选题中具体说明。

## 3. 比较方法

可将先进先出作为基线，在相同输入和到达序列下比较其他策略。评价优先级判断方法时，固定下游调度策略；评价调度策略时，固定优先级来源，便于解释各环节效果。

建议覆盖混合长短请求、突发交互请求、连续后台请求及低优先级持续等待。按业务类别或预先定义的约定分组统计，保存所有请求的完成与失败状态。

采用决策模型时，将调用耗时、失败和资源／调用开销计入端到端记录。分析高优先级收益、其他请求等待变化与整体吞吐。

## 4. 记录与展示

记录实际到达、判断开始／结束、入队、分配、首次生成和完成时间；保存优先级来源、判断结果、动态调整、slot、取消及重试事件。

前端展示等待队列、优先级、执行顺序及各类请求指标。可比较等待时间、TTFT、P95、期限达成率、低优先级最大等待时间、完成率、吞吐及决策开销。
